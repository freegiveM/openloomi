## 2. 真正的 bug（之前没人发现的）

**`while (sep !== -1)` 死循环**：在 [`src/agent.ts`](file:///D:/openloomi3/openloomi/benchmark/GDPval-AA%20v2/openloomi-runner/src/agent.ts) 的 SSE 解析段，`sep` 用 `const` 声明在循环外，循环里 `buffer = buffer.slice(sep + 2)` 后 `sep` 不会重新计算。结果是：拿到首字节（96 字节 session frame，1 个 \n\n）后：

1. `sep = buffer.indexOf("\n\n")` = 94
2. while (sep !== -1) 进入
3. record 切完，buffer 变 ""
4. for loop 0 events
5. 回到 while (sep !== -1) — **sep 仍是 94 → 死循环**

死循环里**没有 IO**（只是循环 + parseSSERecord("")），所以 `sse_debug.log` 不增长，CPU 飙到 100%（v15 v18 都看到 500+ CPU）。**SSE iter=2 race 永远进不到**。

**为什么之前没发现**：每次 race 第一次进 fs polling fallback（之前没有 fs polling）→ 30 min timeout → 无 run.json。所以"在 while 死循环"这件事被 SSE stall 现象掩盖了，没人深挖循环本身。

**修法**：`let sep` 替代 `const sep`，循环尾部 `sep = buffer.indexOf("\n\n")` 重新计算。已应用。

## 6. 已知不可恢复字段

| 字段 | 原因 |
|---|---|
| `response / text` | OpenLoomi 探针只 dump type + keys，**不 dump content**。fs polling 收不到 text |
| `tool_calls` 列表 | 同上 —— 探针不 dump `name`，只能数 `tool_use` 事件数 (`turn_count`) |
| `usage.input_tokens / output_tokens` | 探针不 dump `usage` 字段 |

**如果将来要恢复这些**：改 `apps/web/.../route.ts` 探针，让它把 message 的 `name` / `content` / `usage` 也 dump 出来（注意 message content 可能很大，要控制长度或写到独立文件）。
